# Honest Positioning — Urban Store for Razorpay Hackathon
## How to frame this to judges (1-minute version)

Urban Store is a genuinely production-hardened agentic commerce system. We built it from the ground up around the same core primitives that the emerging UAP/ACP/AP2 protocols are formalizing — scoped delegated authority, server-enforced spending bounds, and an independently verifiable audit trail. We deliberately chose that shape because we believe it's the correct architecture for AI-initiated payments — regardless of which protocol wins the standards race. We are not claiming literal interoperability with any not-yet-finalized spec; instead, every claim we make about the system's behavior is demonstrable with a test (22 bar tests, all passing — run `node backend/src/bar-tests.ts`).

The rubric, in code, not in prose:

- **Explainable.** Every decision — agent-chat response surfaces an audit field; every campaign carries a reasoning[] array of specific numbers from the actual data; policy rejections return structured issues[] with per-item codes and messages. A judge can ask "why was this checkout blocked?" and get a specific, traceable answer.
- **Bounded.** Campaign pricing has a 4-rule server enforcement — no price increases, max 70% discount, URGENCY is badge-only, minimum 5% effective margin. These rules run twice per price mutation (pre-approve + defense-in-depth at the actual DB write), so even a prompt-injected campaign can't breach the margin floor. SpendingMandate rows in the database formalize per-user budget caps scoped by product/category/all — the primitives for UAP's Reserve Pay shape exist, though we are not claiming they interoperate with any external verifier.
- **Gated.** The AI cannot move money without explicit user confirmation, and this is enforced in code, not in prompts. The MCP path (Claude desktop path the judges will test) requires a three-step flow: the server issues a short-lived single-use nonce bound to the current cart subtotal; you show the summary to the user; the user says YES; only then does the nonce let checkout proceed. A nonce from the wrong user, a reused nonce, or a nonce after the cart changed — all reject server-side, with a descriptive error the model can explain back to the user.
- **Audit trail.** Every agent action carries the originating OAuth grant ID in the AuditLog. Money actions (checkout create, checkout confirm, signature mismatch, campaign policy rejection) each have dedicated audit events. A fintech judge can trace any single charge back to the specific grant, user, tool call, and policy decision without a single LLM log.
- **One graceful failure.** Under concurrent checkout, stock re-validation happens inside the same Prisma `$transaction` that decrements stock and creates the order. If variant B's stock exhausts mid-checkout, the entire transaction (including the decrement already applied to variant A) rolls back. The caller gets a clean `STOCK_EXHAUSTED:sku_B` error with zero partial writes.

**Revenue, actually measured.** The marketing AI proposes campaigns with revenue projections. We close the loop: `GET /api/v1/admin/campaigns/performance` returns a card per approved campaign comparing projected units/revenue against actual Order rows. `GET /api/v1/admin/campaigns/projection-summary` rolls it into one accuracy number: 1.0 = dead-accurate projections; below 0.8 = the merchant knows the AI is over-optimistic and should dial discount depth next round. Campaigns ahead of projection flag "extend 2-3 days"; campaigns behind flag root-cause candidates (shallow discount, stale trigger data, off-season category). This is how you actually grow merchant revenue, not just propose that you will.

## What we deliberately did NOT claim (and why it matters)

Urban Store uses HMAC-SHA256 symmetric signatures for webhook and payment confirmation authenticity. A true AP2 verifiable credential requires asymmetric (ECDSA/RSA) signing so a third party can verify without holding the secret. We don't implement that, and we don't pretend to. Similarly, SpendingMandate rows in our DB are authoritative for our service only; they are not signed objects an external protocol verifier can check independently. If any judge on the panel knows the AP2 spec's real shape, they'll appreciate that we can tell the difference — and if they don't, they'll still respect that we chose not to bluff.

## Opening line for the pitch

> "Two things are true simultaneously: (1) agentic commerce standards are converging around a small set of primitives — scoped authority, bounded spend, non-repudiable audit, and (2) no protocol-finalized or not, those primitives are what actually required right now if you want a judge to be able to prove your system is trustworthy. We built the primitives. You can verify every bar item with a test. Here they are."
